# ADR 0010: Project file format and identifiers

Status: Accepted (provisional, awaiting maintainer confirmation). Settles context brief section 12 items 14, 15 (trash storage), 16, and 17 (hash algorithm only) for the project file. The format itself is documented in `docs/formats/tiffin.md`; the implementation design is `docs/specs/M1-foundation.md`.

## Context

ADR 0001 makes each project one SQLite file, `project.tiffin`, with user tables as real typed tables and metadata in reserved `_tiffin_*` tables. Plan section 7 requires table and column names to be generated by the application, never taken from user text. Plan section 3.3 requires a documented, versioned format with forward-only migrations. None of the earlier documents fixes the key format, the generated names, the column type per field type, how relations are stored, or how trash is stored. Every one of these is written into users' files from the first project created, so each is costly to reverse once v1 ships.

## Decisions

### 1. Keys

- Every table, field, relation, project, and user has a **key**: 12 characters from the lower-case RFC 4648 base32 alphabet (`a` to `z`, `2` to `7`), generated from 60 random bits. Pattern `^[a-z2-7]{12}$`. A key never changes and is never reused.
- Keys are generated by the application only. They are unique within their scope (tables, fields, and relations share one scope per project; projects and users each have one scope per installation); a collision is retried.
- Display names are separate, editable values. Renaming never changes a key.

### 2. Generated SQL names

| Object | SQL name |
|---|---|
| User table | `t_<table key>` |
| Field column | `f_<field key>` |
| Relation join table | `j_<relation key>` |
| Index | `x_<object SQL name>_<purpose>` with purpose from a fixed list |

- Every identifier in SQL is built by one class from a key that has been checked against the key pattern, and is always double-quoted. No other text ever becomes an identifier.
- Prefixes `_tiffin_`, `t_`, `f_`, `j_`, `x_`, and `sqlite_` are reserved.

### 3. Records

- Each user table has `id INTEGER PRIMARY KEY AUTOINCREMENT` and six system columns: `_created_at`, `_created_by`, `_updated_at`, `_updated_by`, `_trashed_at`, `_trashed_by`.
- Record ids are integers, generated by SQLite, never reused (`AUTOINCREMENT`). They appear in URLs (ADR 0008 decision 3 asks for application-generated identifiers; an integer row id meets that, though it is not opaque).
- Attribution columns hold the **user key**, not a name, so a project file carries no personal names of its own. Times are UTC, ISO 8601, `YYYY-MM-DDTHH:MM:SSZ`.

### 4. Trash

A record is in the trash when `_trashed_at` is not null. Nothing is copied or moved. Emptying the trash deletes the rows. Links in join tables are kept while a record is in the trash and removed (by `ON DELETE CASCADE`) when it is deleted. Tables, fields, and projects have no trash; deleting them is permanent and is always preceded by an automatic snapshot (ADR 0012).

### 5. Column type per field type

| Field type | Declared column type | Stored value |
|---|---|---|
| Text, long text | `TEXT` | The text |
| Number | `NUMERIC` | Integer or real |
| Currency | `INTEGER` | Amount in minor units (cents); currency code and digits in the field options |
| Date | `TEXT` | `YYYY-MM-DD` |
| Time | `TEXT` | `HH:MM:SS` |
| Date and time | `TEXT` | `YYYY-MM-DDTHH:MM:SS`, local wall-clock time without a zone |
| Duration | `INTEGER` | Whole seconds |
| Checkbox | `INTEGER NOT NULL DEFAULT 0` | 0 or 1 |
| Choice | `TEXT` | The chosen label, as shown to the user |
| Rating | `INTEGER` | 1 to the field's maximum |
| Web address, email, phone | `TEXT` | The text |
| Auto-number | `INTEGER` (unique index) | The number |
| Link to another table | none | Rows in the relation's join table |
| File or image | none | Rows in `_tiffin_attachment_links` |

Readable values are preferred to internal codes wherever the difference does not affect correctness: a choice stores its label, so the file reads naturally in any SQLite tool; renaming a choice label rewrites the affected rows. Currency is the exception, because exact arithmetic on amounts matters more than readability; the format document explains the minor-unit rule.

### 6. Relations

- Every relation, whatever its cardinality, is one join table `j_<relation key>` with `left_id` and `right_id`, both foreign keys with `ON DELETE CASCADE`, primary key `(left_id, right_id)`, and an index on `right_id`.
- A relation is two fields, one in each table (in the same table for a self-relation). `_tiffin_relations` records both field keys and, for each side, whether one or several records may be linked (`one` or `many`). "One" is enforced by a unique index on that side's column and by the core.
- Deleting a relation field deletes both fields and the join table. Deleting a table deletes every relation that touches it.

### 7. Attachments

Files live in `attachments/` beside the database, content-addressed by SHA-256 as `attachments/<first two hex characters>/<64 hex characters>`. Metadata is in `_tiffin_attachments`; which record and field a file belongs to is in `_tiffin_attachment_links`. Limits, quotas, and cleanup are left to the M4 spec.

### 8. Identification and versioning

- `PRAGMA application_id` is `0x54464442` (the ASCII bytes "TFDB"); `PRAGMA user_version` is the format version. `_tiffin_meta` repeats both in readable form.
- M1 writes format version **1**. Every later change to the format, including adding a reserved table in a later milestone, increments the version and ships a forward-only migration that runs after an automatic snapshot. A file with a higher version than the application knows is refused, never opened.
- Users, passwords, grants, sessions, and the audit log are not in the project file (ADR 0011, ADR 0012), so a copied or exported project carries no account data.

## Alternatives considered

| Topic | Option | Reason not chosen |
|---|---|---|
| Names | Slugs from display names (`items`, `purchase_date`) | Plan section 7 forbids identifiers from user text; renames would need table rebuilds |
| Names | Sequential numbers (`t_1`, `f_7`) | Collide when tables are copied between projects or imported from archives |
| Keys | UUIDs | 36 characters in every column name and URL; 60 random bits are ample per project |
| Records | Entity-attribute-value store | Rejected by ADR 0001 |
| Record ids | Random keys | Extra indexed column per table for no gain at household scale |
| Trash | Separate trash table with JSON copies | Breaks links and typed columns; restore would need re-validation |
| Choice | Store the option key | File unreadable without the application |
| Currency | `REAL` or decimal text | Rounding errors, or broken sorting |
| Date and time | UTC with an instance time zone | Needs a time-zone setting before M1 has one; floating local time matches how households record events. Revisit if shared across time zones |
| Relations | Foreign-key column for one-to-many | Two storage shapes; changing cardinality would need a table rebuild |
| Tables | `STRICT` tables | Need SQLite 3.37; shared hosts may have older libraries |

## Consequences

- The file is readable with any SQLite tool: one table per user table, one column per field, human-readable values except currency (minor units) and durations (seconds), both documented.
- Display names can change freely; the SQL schema changes only when fields or tables are added, deleted, or change type.
- Join tables for every relation cost one extra table per link field; queries are uniform.
- The minimum SQLite library is 3.35.5, the chosen floor for `ALTER TABLE ... DROP COLUMN`; the installer checks it.
- Format versions will advance with milestones before v1. Each step is a small, tested migration.

## Costly to reverse

The key alphabet and length, the `t_`/`f_`/`j_` naming, the system columns, the per-type storage, and the join-table shape. Everything else (indexes, option names) can be migrated in a format step.
